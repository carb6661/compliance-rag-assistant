# 项目复盘与面试讲述：不是“套壳聊天”，而是可验证的资料证据链

## 0.5：来源授权进入检索、模型材料和最终证据（2026-10-29）

**项目背景**：0.4限制谁能查询、维护或请求外部生成，但普通查询者仍可检索整库。两份资料即使属于不同分析员，只要标准/版本/级别相同，就会进入相同候选集。这个问题不能靠更复杂的提示词、版本过滤或提高相似度阈值解决。

**设计思路**：在同一个SQLite库增加来源读ACL，使用服务端认证身份和当前凭据绑定，直接参与检索SQL。只让获准的块/向量进入BM25统计、Dense/RRF与上下文；维护接口使用独立ACL ETag，授权变化、正文替换都进入原全局修订机制，分别在评分后、生成前和发布前复核。维护者可信且全库可见，不把管理员权限误当普通用户隔离。

| 技术问题 | 技术原因 | 最终方案及实际证据 |
| --- | --- | --- |
| 同scope不同来源一起被读 | 业务适用范围不表示身份权限 | SQL EXISTS在评分前做来源读ACL；两份同scope合成文档分别180/999天，Alice/Bob只得到各自引用 |
| top_k后再删未授权结果仍有影响 | 未授权文本可能已影响BM25语料统计、占据名次或进入模型 | 评分只接收获准rows；三模式的授权结果/分数等于仅授权语料的参考库（独立库ETag按设计不同），模型替身只收到获准来源 |
| 只绑定身份名会继承旧权限 | 新凭据或同名新身份沿用旧ID | ACL绑定ID+凭据摘要；新令牌默认无权限，重新授权后旧令牌绑定不再匹配；不向客户端返回摘要 |
| 修改正文后旧授权继续开放新内容 | 允许的是来源标签，未必是新正文 | 实际正文/配置替换同事务清空读者并报告数量；no-op保留，删后重建不继承；旧授权标签412 |
| 两个维护者覆盖彼此授权 | source ETag只表示内容，不能标识ACL集合/撤权ABA | 独立access ETag绑定来源状态、授权generation和凭据集合；事务内CAS，8连接1提交/7冲突 |
| 生成时撤权仍可能发布旧资料 | 开始时有权不代表结果发布时仍有权 | 修订+当前权限检查，受控selector运行中经实际维护接口撤权，最终清空answer/citations/hits及候选数；生成前变化则不调用selector |
| 升级默认整库开放会扩大权限 | 旧库没有读者清单可可信推断 | schema2→3默认空ACL，维护者逐来源审阅开放；独立12块旧库验证原块、source ETag、修订保持，故障回滚新列/表/标记 |

**实际验证**：完整280项本地测试（原227项按来源授权合同回归，新增53项），真实Uvicorn回环HTTP验证无授权→授权→正文替换后再无证据，进程内ASGI复现隔离、生成中撤权与重审。真实512维BGE在禁止出站socket/DNS下通过两块/三检索模式的来源检查；原20问开发集指标不变，仍只拒3/4无答案题。selector是本地受控替身，不是实际LLM，不把这次权限检查写成语义准确率提升或公网攻击防护率。详见[来源设计与操作](SOURCE_AUTHORIZATION.md)、[固定证据](../examples/evaluation/source-access.json)、[验证记录](VALIDATION.md)。

**亮点与岗位能力**：把AppSec对象授权落入真实RAG数据路径，而非只在路由上加角色；同时考虑候选、统计、模型输入、引用输出、凭据轮换和资料维护。能解释“角色/业务范围/来源权限/内容修订”四者各管什么，以及为什么撤权检查不能撤回已经传给服务商的材料。

**可核验简历模板**（亲自复现并确认本人贡献后使用，注明AI辅助）：

> 在合规资料RAG原型中实现SQLite持久来源读ACL，将服务端身份及凭据绑定作为BM25/BGE/RRF评分前过滤条件；设计独立授权ETag、资料变更重审及生成前后修订复核，覆盖同scope跨来源读取、授权ABA、轮换继承和中途撤权。新增53项授权/事务/迁移回归，完整280项测试通过；以原创合成资料验证，不作为企业生产或真实测评经历。

**面试复现**：运行source_access_demo，说明为什么两份同标题/同版本资料仍须分别授权；给出固定报告中Alice来源、selector来源和撤权后空证据；再运行live_smoke展示实际HTTP与更新重审；打开SQL及BM25参考库回归，解释过滤必须早于评分；最后展示独立schema2迁移/回滚和权限仍有检查后发送窗口的限制。

**未完成**：真实IdP/令牌在线撤销、租户命名空间、段落ACL、操作者审计、独立worker硬截止/持久任务状态、真实生成质量与独立标注集。来源ACL可在线更新，但检查后到发送/外传之间仍有窗口，服务商已收到的材料无法撤回。以下0.4/0.3/0.2为历史设计与当时证据，不将其旧限制冒充当前新增成果。

## 0.4：从“本机能连上就能改库”到有权限、有额度的RAG入口（2026-10-27）

**项目背景**：安全分析员可以用这个助手定位不同版本/级别的资料依据，但业务闭环不能只保证“引用正确”。0.3虽然挡住陈旧草稿，匿名调用者仍可先读当前来源、拿ETag再更改；多个客户端也可同时触发昂贵嵌入或外部生成。ETag、回环绑定、Host检查分别解决不同问题，都不能认证操作者。

**设计思路**：沿用原FastAPI、SQLite和生成模块，增加服务端静态令牌身份。reader只检索/抽取，analyst可请求生成，maintainer可解析/维护和看完整索引/trace；外传仍须管理员显式启用。先认证和查角色，再在正文读取前获取全局/身份额度，进入真正生成工作前再取得llm额度；完整保留原有ETag和引用校验，权限不能替代并发一致性。

```text
HTTP → Host → 令牌摘要/角色 → 滚动频率 + 全局/身份任务槽
     → 有界JSON → 同步worker占用 → 可选生成任务槽
     → 原入库/条件写 或 范围过滤/检索/引用校验
     → HTTP结束 + worker实际结束 → 归还任务槽
```

**实际遇到的技术问题与最终方案**：

| 问题 | 原因 | 方案和证据 |
| --- | --- | --- |
| 在路由依赖中认证太晚 | JSON可能先读入，未授权请求已消耗入口资源 | 纯ASGI中间件在receive前校验身份/路由及名额；用会抛异常的receive证明401/403/429不读正文 |
| 给“查询用户”生成权限过大 | llm也是ask接口的一个字段，但会向外部服务传资料 | reader的llm模式在服务初始化/检索前403；有生成器时也断言调用次数为0 |
| HTTP取消后实际并发超限 | 请求协程取消不会终止已经开始的同步线程，单一finally可过早归还信号量 | 同一锁下记录HTTP和worker两类占用，只有都结束才归还；真实ASGI取消+AnyIO工作线程仍占名额，线程结束恢复0 |
| 只在worker抢槽仍会大量缓冲正文 | 请求已经排入线程池，入口内存不受那个槽控制 | 正文前先准入，无应用排队；同一身份8请求实际1个200/7个429 |
| 并发读取频率可能超发名额 | 检查与追加分开会竞争，整分钟桶还有边界突发 | 单调60秒滚动队列、同锁检查/计数；32并发仅5次频率放行，精确60秒旧项过期 |
| 服务配置坏了却退回匿名模式 | 把“不配置/解析失败”都视作禁用鉴权 | 未配置锁定503，损坏配置启动失败；无内置生产凭据，令牌随机生成且不打印 |

**实际验证**：Windows/Python3.12.8完整 **227项测试通过**，原167项按认证合同迁移，新增60项。真实回环HTTP确认无认证401、reader写403、reader抽取200、reader llm403；进程内ASGI固定实验1放行/7容量拒绝，模型替身只执行1次，另一身份的本地抽取可继续。还有异常、超限正文、双Authorization、配置损坏、先取消后worker启动等回归。参见[完整设计/复现](ACCESS_CONTROL.md)、[固定证据](../examples/evaluation/access-admission.json)、[验证记录](VALIDATION.md)。selector是明确的本地测试替身，不是实际LLM质量或网络压测。

**项目亮点/岗位能力**：把AppSec的最小权限和资源边界落到已有RAG真实业务路径；区分“能连接、能查询、能外传、能维护”；用取消反例解释异步HTTP和同步worker的生命周期差异。能够现场从返回状态、数据修订和真实调用计数说明结果，而非只展示一个Bearer装饰器或成功聊天截图。

**可写进简历的模板**（需你亲自复现并确认贡献；如实注明AI辅助）：

> 在已有合规资料RAG原型上实现默认锁定的令牌角色权限与单进程有界准入，分离只读检索、外部生成及资料维护；通过正文前频率/任务限制和HTTP/同步worker双生命周期占用处理取消后并发名额提前释放问题，新增60项权限、额度、异常及取消回归，完整227项测试通过。仅本地共享库实践，未接入生产身份服务。

**面试复现顺序**：运行access_demo，解释401/403/200/403及1/7；运行live_smoke展示真实HTTP与ETag继续生效；打开取消回归，展示HTTP取消时total仍为1、worker退出才为0；最后解释reader可见所有导入资料、为什么必须单worker、为什么没有费用预算和硬任务截止。不要把这些数字写成吞吐量提升、企业用户量或防护有效率。

**当前局限与下一步**：本轮只增加静态角色，不等于文档ACL/租户隔离、IdP登录、在线撤销或操作者持久审计。频率进程重启清零，多实例不共享；被授权慢客户端/持续输出的上游仍可占槽，下一步需要有硬截止的独立worker和持久任务状态。此轮没有改检索阈值/20问开发集，相关但无事实的误答缺口仍在；真实生成与独立标注仍未验证。下文保留0.3/0.2历史问题与当时证据，勿把旧版本限制当成新增成果。

## 0.3：让资料维护不再无声覆盖新知识（2026-10-25）

**背景**：同一个分析员也可能有两个编辑终端。A提交更正后，B的旧草稿仍可能覆盖A；向量检索无法挽救已经被旧资料替换的知识库。0.2虽有原子事务，但没有比较草稿基于哪个来源修订，这两种问题不能混为一谈。

**设计**：新增来源读取与ETag、create-only、新建/替换/删除的显式条件。预检查挡住已陈旧请求，向量计算后在IMMEDIATE事务中重新比较再写；来源generation加库身份防止“改回原文/删除重建”令旧标签复活。

**实际技术难点**：只用正文哈希挡不住ABA；只在解析前检查挡不住向量计算期间的竞争提交；把全局revision放进来源读取JSON又不改来源ETag，会使同标签对应不同表示。最终区分全局查询修订与来源generation，来源表示不混入其他来源变更，事务内重复比较。

**验证**：本地167项测试；真实回环HTTP `[428,200,412,412]`；8个连接1次提交/7次冲突，另真实4个CLI子进程1次成功/3次冲突；独立schema1夹具迁移保留原12块，注入故障回滚列与settings。详见[条件维护设计/限制](CONDITIONAL_WRITES.md)及[固定证据](../examples/evaluation/conditional-writes.json)。0.2的风险来自代码分析，没有把模拟旧服务当成实际旧版攻击证据。

**亮点与可用表述**（仍须亲自复现、确认本人贡献，注明AI辅助）：为RAG知识维护实现来源级乐观并发控制，在SQLite事务内复核ETag，覆盖旧草稿、陈旧删除、两类ABA和schema升级回滚，使知识更新与检索证据状态保持可解释一致性。

不把ETag当权限令牌，不声称新增了多用户鉴权、分布式一致性、历史版本存档或提升语义答案质量。原有4个不可回答问题只拒3个的缺口和真实生成服务尚未联调的边界保持不变。

## 项目背景

场景是安全工程师/合规分析员在多个版本、不同安全级别的资料中定位依据。通用聊天的实际问题是：它可能找到主题相似的旧版内容，引用到错误级别，或给出一个无法回到原文的数字。原项目只解决标题切分，缺少存储、检索、回答及评测，不能称作可用的问答系统。

0.2沿用同一仓库的结构化解析器，构建本地私有资料工作流：可导入、重启后查询、明确过滤范围、看到原文出处、更新/删除后验证结果，并接入服务端配置的兼容模型。所有公开资料原创合成，不上传受限标准或虚构真实测评结果。

## 设计思路

```text
合法Markdown + 明确配置
  → 严格层级解析 + 原文区间
  → 可选本地BGE向量 + SQLite事务入库
  → 必填标准/版本/级别的SQL过滤
  → BM25 / 精确余弦 / RRF混合检索
  → 有界上下文 → 抽取基线或兼容LLM选摘
  → 引用ID + 连续原文 + 区间校验
  → revision复核 → 证据答复 + 最小化trace
```

选择SQLite和精确向量扫描，是因为当前目标是小型、单人、可复现原型（上限2000块），不为了简历堆砌Qdrant/Kafka/Kubernetes。选择本地中文BGE，避免把随机/哈希向量冒充真实语义检索；生成模型可换服务商，但地址与密钥不由请求控制。

输出是证据选摘而非自由合规判定：引用完整性可以用程序验证，完整事实蕴含目前做不到，就不声称已经做到。这是业务风险取舍，不是“提示词写得足够长就没有幻觉”。

## 真正遇到的问题、方案和证据

| 问题 | 技术原因 | 本次方案 | 如何验证/剩余风险 |
| --- | --- | --- | --- |
| 同一问题混出旧版/其他级别数字 | 相似度不理解业务适用范围，先检索再过滤可能丢候选 | 标准编号/版本/级别必填，先SQL过滤，BM25统计也在过滤后 | 同问四种范围分别得到30/90/60/180天；未过滤基线出现38个越范围hit，过滤后0；不是租户授权 |
| 真实向量检索大面积误拒绝 | 直接设0.72阈值；正确top1的cosine大多0.54–0.72 | 保存逐问分数探针，将开发阈值调整为0.50，保留前后报告 | Dense Hit@3从1/16到16/16；阈值同集调参，不能宣称泛化准确率，相关无事实仍有问题 |
| 混合检索未必胜出 | RRF名次融合与同分规则会保留词法噪声 | 三模式同集对照，返回BM25/cosine/RRF证据，不伪造提升 | BM25与Hybrid MRR@3均0.96875，Dense为1.0；没有证明Hybrid更好 |
| 引用编号真实但原文被模型改写 | JSON合法不代表内容可信 | schema/ID/连续原文/重复/finish_reason校验，再计算精确来源区间 | 伪造期限、错误ID、重复quote、额外字段、截断返回均拒答；仍不证明摘录相关性 |
| 长块被嵌入器静默截断 | 解析目标是字符，而模型容量是token；表格还可能原子超长 | 使用真实分词器无截断计数，超过512拒绝并要求显式重切 | 真实ONNX集成测试验证超长拒绝；未提供token-aware表格重排 |
| 更新后旧块/旧答案残留 | 只新增向量没有删除，或模型生成期间资料已变化 | 同源文本/块/向量同事务替换，删除级联；模型结束复核revision | 替换、失败回滚、并发相同导入、生成中删除回归；最终复核后发送窗口仍在 |
| API/模型错误泄漏输入或凭据 | 默认验证异常、模型服务异常可能带请求 | 本地env密钥、请求不能改provider、错误静态化、不记录问题/正文 | Mock契约覆盖401/429/重定向/超时/超大返回；并非真实服务商联调 |
| 小样本全绿掩盖拒答缺陷 | 主题相关不意味着资料含所问事实 | 专门加入“进入记录加密算法”无答案题，保留失败 | 四个不可回答题只拒答3个，拒答率75%；不包装成100%回答正确 |

前后报告：[修正前](../examples/evaluation/semantic-before.json)、[修正后](../examples/evaluation/semantic-after.json)。全部属于12块/20问开发集，不是独立测试集或真实客户评估。Hit@3针对16个可回答题；MRR是正确证据名次的倒数平均，不能等同生成答案事实正确率。

阈值降低也有代价：Dense的不可回答拒答从4/4降到3/4。面试时应解释召回与拒答之间的取舍，而不是只摘取16/16宣传“效果全面提升”。

## 项目亮点

1. **纵向完整**：从可信范围定义、持久更新，到检索、回答、引用验证和追踪的业务闭环，而不是只有切分或聊天接口。
2. **出处可复核**：保留原解析器的标准/级别/安全类与精确源码区间，将回答quote映射回原文。
3. **真实而非模拟语义模型**：本地实际运行512维中文BGE，模型/分词器字节摘要绑定索引；Mock只用于适配层故障测试且明确区分。
4. **有反例的评测**：同时报告召回、名次、越范围结果、不可回答拒答和实际单机耗时；公开失败，不只截图成功回答。
